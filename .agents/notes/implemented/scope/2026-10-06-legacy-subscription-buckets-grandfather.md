# Agent Note: 历史订阅积分桶的周期清零迁移决策(grandfather)

Status: implemented — PR #151 外部审核发现(P1-151-05)裁定:存量桶 grandfather(不追溯补周期边界)

## Problem

PR #151 起,订阅续费发放的积分桶带 `expiresAt = 周期末`(周期清零语义)。但已部署实例的存量订阅桶 `expiresAt = NULL`——过期清扫只扫 `expiresAt IS NOT NULL`,这些桶永远不会被周期清零,形成"新额度清零、老额度永存"的混合语义。

## Decision

**存量桶 grandfather(方案 A)**:不迁移、不回填。

1. 语义上,历史发放发生在此语义变更之前,当时的合同与用户预期是"发出来就是你的"(P0 accumulate 语义);单方面给已发放额度补过期时间属于追溯性合同变更。
2. 财务上,存量订阅额度是已确认的合同负债;清零会立即减少负债、确认 breakage 收入——在没有历史履约数据支撑下这样做不符合审慎原则(需要 breakage 率数据)。
3. 操作上,回填"正确"的周期边界需要知道每个订阅的当前周期末端,而存量数据里该信息可能已过时(与 P1-151-04 同源的 stale 问题),错误回填会造成已付费额度立即过期——比混合语义更糟。

新发放从 PR 合并之日起自然带周期边界;存量桶按其原始语义(永不过期)走完生命周期。升级说明中明示这一差异。

## Alternatives considered

- **方案 B(回填 currentPeriodEnd)**:否决,理由如上 3;且不可逆。
- **惰性迁移(下次续费时给旧桶补边界)**:否决——把迁移语义藏进运行时路径,审计与对账无法静态推演。

## Consequences

- 升级实例在过渡期存在混合语义:控制台 /credits 的"即将过期"区块只显示新桶;存量桶通过"按类型余额分布"可见。在 UI 上不区分(分布表本就不按桶展示)。
- 若未来真实需求要求统一(如积分商城),届时按用户粒度提供自愿的"余额合并/转换"工具,而非单方面回填。
